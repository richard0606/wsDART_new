# 量化部署经验总结（ONNX → .bin → RDK X5 板端）

> 汇编时间：2026-10-17　　适用：`yq_dart_aim` 模型识别模式走 RDK X5 BPU。
> 本文把「x86 量化编译」到「板端集成、验证、实跑」的完整经验、注意事项与可复现方法
> 汇总在一起。量化工具链细节见 `BPU部署指南.md`，本文侧重**实战经验与踩坑**。

---

## 0. 最终方案（TL;DR）

- **最终用的是 CoordAtt 版**：`model/praysky_coord_576x768.bin`（≈5MB）——
  **不是 c2psa**。c2psa cut 的 `.onnx` 只是 `model_path_cpu` 备用配置里的残留，
  当前 `infer_backend: BPU`，不参与运行。
- 量化源：`praysky_coord_noe2e_0331_576x768.onnx`（496 节点）在 `/Transpose_output_0`
  处 cut 掉内置 NMS 后量化编译。
- 为什么弃用 c2psa：它有两个 Softmax 落在 CPU（模型被切成 3 段 subgraph），
  作者本人也警告过 PSA Softmax 量化不友好；CoordAtt 是纯卷积 + Sigmoid，
  checker 零 warning、**单 subgraph 全 BPU**。代价是 mAP 0.89→0.87（作者数据）。
- **为什么必须 cut**：完整模型内置 `NonMaxSuppression` / `NonZero`，地平线运行时
  **不支持**（连丢 CPU 都不行），带着它们编译直接失败。
- 实测结果：板端单帧全流程 **~22ms（≈45fps 上限）**；与 float 模型对比，
  清晰目标置信度差 **0.03~0.08**、类别稳定。

## 1. 全流程方法（可复现）

### 1.1 x86 量化侧

```python
# ① 切模型：丢掉 NMS 后处理，接口变成 (1,9072,28)
import onnx
from onnx.utils import extract_model
extract_model('praysky_coord_noe2e_0331_576x768.onnx',
              'praysky_coord_576x768_cut.onnx',
              ['images'], ['/Transpose_output_0'])
# 校验：输出必须是 [1, 9072, 28]
```

```yaml
# ② hb_mapper 配置要点（完整版见 BPU部署指南.md §3.3）
model_parameters:
  march: 'bayes-e'            # RDK X5
input_parameters:
  input_type_rt: 'nv12'       # YUV 转换在 BPU 内部做，最快；CPU 侧只做 BGR→NV12
  input_type_train: 'rgb'
  input_shape: '1x3x576x768'
  norm_type: 'data_scale'
  scale_value: 0.00392156862745098   # 1/255
calibration_parameters:
  cal_data_dir: './calib'
  calibration_type: 'default'        # 精度不够改 'mix'（敏感节点 int16）
```

```bash
# ③ 编译（容器必须 root 跑：工具链 torch 装在 /root/.local）
docker run --rm -v ~/horizon_work:/work -w /work \
  openexplorer/ai_toolchain_ubuntu_20_x5_cpu:v1.2.8 bash -c "
    hb_mapper checker --model-type onnx --march bayes-e --model praysky_coord_576x768_cut.onnx
    hb_mapper makertbin --config dart_576x768.yaml --model-type onnx
    rc=\$?; chown -R $(id -u):$(id -g) /work; exit \$rc"
# 约 40 分钟出品：model_output/praysky_coord_576x768.bin
```

**先跑 checker 再花时间量化**：checker 不耗标定图、几十秒出结果，能提前暴露
不支持的算子（尤其 `NonMaxSuppression` / `NonZero` 这类「不可落 CPU」的）。

### 1.2 标定图（直接决定量化精度）

- **必须与推理预处理一致**：训练/标定/推理三处都用 letterbox（等比缩放 + pad 114）
  到 576×768。工具链自己只会 resize，所以要**预先 letterbox 好**再放进 `calib/`。
- `calib/` 目录里**只能放图片**（混进 .md 会让 skimage 报错）。
- 用真实赛场画面（同相机、同曝光/增益），100~300 张，覆盖不同光照/距离/角度。
- 素材可复用：`calib_quant/`（base/outpost × c1/c2 各 100 张，实拍）与
  `~/下载/校验集` 同源。

### 1.3 板端部署侧

```yaml
# src/yq_dart_aim/config/params.yaml
use_model: true
infer_backend: BPU
model_path_bpu: /root/dart_ws_on/src/yq_dart_aim/model/praysky_coord_576x768.bin
conf_threshold: 0.25
model_nms_threshold: 0.7      # 同类框 IoU NMS，与模型内置 NMS 一致
```

```bash
colcon build                  # CMake 自动探测 libdnn，把 BPU 后端编进程序
# 重启服务（systemd）或 ros2 launch yq_dart_aim start.launch.py
# 运行期热切后端 / 改模型路径 / 调阈值：
ros2 param set /dart_aim_node infer_backend BPU
```

### 1.4 三层验证法（从易到难，全部实际用过）

| 层级 | 做法 | 证明了什么 |
|---|---|---|
| L1 离线 | PC 上：完整 ONNX（内置 NMS）当标准答案 vs cut+自研后处理，同图对比 | 后处理逻辑对（top1 逐位一致） |
| L2 板端离线 | 独立小程序：同一帧分别过 `.bin`（hobot_dnn）与 float cut（ORT），比类别/框/置信度 | 量化损失是多少、NV12 链路对不对 |
| L3 实况 | 把校验图**注入 `/image_raw`** 走真实节点链路（cropCenter→letterbox→NV12→BPU→解码+NMS），肉眼看调试图 | 端到端全对（例：离线 0.780 ↔ 画面 78%） |

L3 的注入法很好用：不用真靶子、不用改代码，一张图就能验证整条链路（注：异步推理
下结果落后一帧，亮暗帧交替时框会画在上一帧的位置，属正常现象）。

## 2. 模型接口与板端实现要点（全部为实测值）

| 项 | 实测结果 | 对应实现 |
|---|---|---|
| 输入 | `IMG_NV12 [1,3,576,768]`，**stride 读出全 0**（运行时按紧凑布局） | `model_backend_bpu.cpp`：BGR→I420→NV12，`y_stride<=0` 时回退宽度 |
| 输出 | **F32 `[1,9072,28,1]`**！不是文档猜的 S16 `[1,9072,28]` | 解析要「剔除 size=1 的维」再取 (N,C)；scale=1 无需反量化 |
| 28 布局 | `box(4) + cls(12) + color(4) + kpt(8)`，全为 sigmoid 后/已解码 | `model_detector.cpp decode()` |
| 后处理链 | argmax → conf≥0.25 → top300 → **同类框 IoU NMS(0.7)** → 坐标反解 | 同上 |
| 坐标反解 | letterbox：(x−pad)/scale，映射回 1280×720 裁剪图坐标系 | `LetterboxMap` |
| 性能 | 全流程（含 BGR→NV12）均值 22.13ms、p50 21.78、p95 24.18 | 推理线程单帧串行 → 上限 ~45fps |

**NMS 用「框」不用「4 关键点四边形」**（重要经验）：
量化模型的关键点跨 anchor 抖动很大（实况帧实测角点 451↔464、232↔244 这样跳），
同一目标的候选框 IoU 稳定 0.78~1.0，但关键点四边形包围框 IoU 会在 0.47~1.0 乱跳——
会出现两个同类别框（实况真出现过：两条 s0_o6 0.853、框 IoU=1.0，却因关键点 IoU=0.6
没被压掉）。模型内置 `NonMaxSuppression` 的输入本来就是框，用框 IoU 既稳又一致。

## 3. 踩坑清单（坑 → 根因 → 解决）

| # | 坑 | 根因 | 解决 |
|---|---|---|---|
| 1 | checker/编译报 `HorizonRT not support NonMaxSuppression NonZero` | 完整模型内置 NMS 后处理，这两个算子不可落 CPU | `extract_model` 切到检测头输出 |
| 2 | c2psa 模型 2 个 Softmax 落 CPU、切 3 段 subgraph | PSA 注意力 Softmax 量化不友好 | 换 CoordAtt 版 |
| 3 | 以为输出是 S16 `[1,9072,28]` | 文档是推测值 | 实测 F32 `[1,9072,28,1]`，解析按 4D 写 |
| 4 | `cannot reshape array ...`（标定） | 默认 loader 把 PNG 当 float32 二进制读 | `preprocess_on: True` 走图片路径（或预转 .bin） |
| 5 | `Could not find backend ... .md` | `calib/` 混了非图片文件 | 说明文档移出 calib |
| 6 | `docker run python3 - <<PY` 无输出 | 缺 `-i`，heredoc 没进 stdin | 加 `-i` 或挂载脚本 |
| 7 | 产物属主 root 删不掉 | 容器内 root 运行 | 跑完 `chown -R $(id -u):$(id -g)` |
| 8 | 容器非 root 报 `No module named torch` | 工具链 torch 在 `/root/.local`（700 权限） | 老老实实 root 跑 |
| 9 | 量化后置信度低/漏检（边界样本） | 标定/训练预处理与推理不一致；int8 掉点 | 三处统一 letterbox；提高 conf_threshold；必要时 `mix`(int16) 重量化 |
| 10 | 实况出现两个同类别框 | 关键点四边形 NMS 在量化输出上不可靠（见 §2） | NMS 改用框 IoU |
| 11 | 相机 ROI 窗口每次重启跳变（@76/@152/全幅） | 相机节点读 Height 上限在复位 Offset 之前，上限取决于断电前状态 | `roi_offset_y` 固定 76（= 标定时代窗口），不要用 -1 |
| 12 | `.bin`/`.onnx` 误提交 | — | `.gitignore` 已忽略；模型 AGPL-3.0，公开仓库注意许可 |

## 4. 量化精度实测记录（2026-10-16，校验集样本）

| 场景 | float(ORT) | 板端 .bin | 结论 |
|---|---|---|---|
| 清晰 outpost（多帧） | 0.80~0.89 | 0.75~0.85 | 置信度差 0.03~0.08，类别/框稳定 |
| 边界 outpost_c2 | 0.77 | 0.39 | 仍可检出（>0.25），明显掉分 |
| 边界 base_c2 | 0.70(s1_o7) | 0.63(s0_o0)+0.34(s1_o7) | **类别次序翻转**（量化噪声），但仍能取到目标类 |
| R 通道噪声 | — | conf 列最大偏差 0.1~0.6（个别 anchor） | 大多数 anchor 差 <1e-5 |

**结论**：清晰目标放心用；边界样本有类别翻转风险。现场若发现漏瞄/误瞄，
先调 `conf_threshold`；仍不够就 x86 上用 `calibration_type: mix`（敏感节点 int16）
重新量化再走一遍 §1.4 三层验证。

> 注：板端对比里有一部分落差来自 BGR→NV12→BPU 内部转回 RGB 的颜色往返，
> 不全是 int8 量化的锅；这也是 nv12 路线的固有代价（换来的是速度与带宽）。

## 5. 性能记录

| 指标 | 数值 | 备注 |
|---|---|---|
| bpuInfer 全流程 | **22.13ms**（p50 21.8 / p95 24.2） | 含 BGR→NV12 转换 + 反量化 |
| 推理上限 | **≈45fps** | 单线程串行 1/0.02213 |
| 相机（50ms 曝光） | 17.7fps | 当时的实际帧率 |
| 相机（10ms 曝光） | 49.4fps | 瓶颈已转移到模型侧 |
| dart_aim_node CPU | ORT ~380% → BPU ~150~200% | 提升直观可见 |

再想提帧率的方向：预先把 NV12 转换做掉（让 BPU 直吃相机 NV12）、或后处理向量化。
